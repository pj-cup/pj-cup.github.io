# Verify PJ Cup (data + build)

The site is `docs/`, generated by `python3 build.py` from the latest `csv/YYYYMMDD.csv`. This skill checks the data and the build. It doesn't open a browser. The visual check (CLAUDE.md "Verification workflow" step 3) is still manual.

## Launch

There's nothing to launch: no server, no dependencies, Python stdlib only. Run everything from the repo root.

## Doctor

Run this read-only check first, or whenever a result looks wrong:

```sh
python3 --version && ls build.py verify.py && echo "latest: $(ls csv/*.csv | sort | tail -n 1)"
```

It should show Python 3, both scripts, and a `latest:` line naming the snapshot `build.py` will use. An empty `latest:` means `csv/` has no snapshots.

## Drive

```sh
.claude/skills/verify-pj-cup/scripts/check.sh                  # latest snapshot
.claude/skills/verify-pj-cup/scripts/check.sh csv/20260919.csv # a specific snapshot
```

Steps the script runs:

1. `verify.py <csv>`: the head-to-head grid mirrors correctly and the standings reconcile.
2. `build.py`: must exit 0, write nothing to stderr (it warns there when the standings and grid player lists diverge), and print `Using latest snapshot: <latest csv>`.
3. Rebuild and compare md5s of every file in `docs/`. They must match.
4. Report `git status --porcelain docs/`. This is informational: after a source change, `docs/` is expected to differ from HEAD.

Exit code 0 means every check passed. 1 means at least one failed.

The CSV argument only changes what `verify.py` checks. `build.py` always builds from the latest `csv/*.csv`, so a non-latest argument doesn't change the build steps.

The script rewrites `docs/` (it runs `build.py`). That's the normal workflow, but don't run it on a tree where someone has uncommitted hand edits in `docs/` they want to keep, since `docs/` should never be hand-edited anyway.

## Evidence

Each run writes `.verify/<YYYYMMDD-HHMMSS>-<pid>/` (gitignored):

- `summary.txt`: one PASS/FAIL line per check and the final `RESULT`.
- `verify.log`: verify.py output, with the list of mismatches on failure.
- `build1.out`, `build1.err`, `build2.out`, `build2.err`: output from both builds.
- `md5-1.txt`, `md5-2.txt`: per-file md5s of `docs/` after each build.
- `docs-diff.txt`: generated files that differ from HEAD.

When reporting, quote the `summary.txt` lines and the evidence path. On a failure, quote the relevant log lines.

## Cleanup

There's nothing to tear down. Evidence directories are kept on purpose. Delete old ones with `rm -rf .verify/<run>` only when the user asks.
